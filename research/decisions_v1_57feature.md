# Design decisions (decided once, 2026-11-21)

- **D1 Framing: confirmed.** Origin week t, features use data <= t only, target = cases at t+h, h in {2,3,4}, one direct model per horizon. Features: lags 0-8 of the five weather columns, rolling rain sums (2/4/8 wk), rolling temp and humidity means (4/8 wk), three static ward indices, sin/cos of the target week-of-year. No `ward_id`, `city` or case lags, so an uploaded file with unseen wards and no case history still works. Case lags are an ablation line only.
- **D2 Models: confirmed.** LightGBM, Poisson objective (58% zeros, counts), early stopping on 2023, fixed seed. Baselines: ward mean, persistence (cases at t), and ward x week-of-year mean, which is the fair seasonal baseline. Fallback if LightGBM fails to install: sklearn HistGradientBoosting Poisson.
- **D3 Split: overridden on refit.** Split by target date: train 2016-2022, validation 2023, test 2024-2025, touched once. Validation and test drop their first 4 target weeks for every horizon, which purges label overlap and scores all horizons on the same weeks. **No refit on train+val:** the shipped model is exactly the evaluated one, and 2023 must stay out of training for the interval calibration (D6) to be valid.
- **D4 Tiers: confirmed.** Thresholds are the P60/P85/P95 of training-period cases: Low < 1, Medium 1 to < 7, High 7 to < 13, Critical >= 13, stored in `thresholds.json`. The same cutoffs define the actual tier (from observed cases) and the predicted tier (from predicted mean). Report High+Critical recall and precision on validation and test. Pre-committed fallback: if validation High+Critical recall is below 0.60, move only the predicted-side cutoffs by rank-matching on 2023. Never on test.
- **D5 Drivers: confirmed.** LightGBM `pred_contrib=True`. Contributions are in log space, so they are summed by family (rainfall, temperature, humidity, ward vulnerability, season) and shown as a percent effect on predicted cases, naming the strongest lag in each family ("rain 3 weeks ago").
- **D6 Intervals (bonus): conformal.** 5th and 95th percentiles of (actual - predicted) / sqrt(predicted) on 2023, per horizon, give a 90% band that widens with the prediction, floored at 0. No extra models. Test coverage is reported in `metrics.json`.
- **(a) What-if weather.** The user sets rainfall (mm), a temperature shift (applied equally to avg/max/min) and a humidity shift for the last N weeks (1-4) before the origin. Edits go to the raw weekly rows, then the same `build_features` runs for that ward, so lags and rolling sums stay consistent. Every control is clamped to the range seen in training, and humidity to 0-100. Output is labelled "scenario", shown next to the unedited prediction.
- **(b) Ranked ward list.** For a city, origin week and horizon: one batch prediction over that city's wards, sorted by predicted cases, with tier, interval and top driver. The same batch output feeds the ward x week heatmap.
- **Metrics.** `metrics.json` holds MAE, RMSE and Poisson deviance by horizon and by year for the model and all three baselines, tier recall/precision, interval coverage, and measured inference time. Docs quote only this file. Fixed before the test run: **test MAE and RMSE are the headline comparison.** Poisson deviance is quoted only for model vs ward mean, because persistence and ward x week means often predict exactly 0 and their deviance then depends on an arbitrary floor. Validation figures are labelled in-sample where 2023 was also used for early stopping or interval calibration, so validation coverage is never quoted as a result.
- **Data honesty.** The dataset is clean and likely synthetic. Max and min temperature are identical across wards within a city-week. Rainfall, humidity and average temperature vary by ward but are partly shared (a median of about 9-10 distinct values per city-week). Docs claim neither real-world validity nor fully independent ward-level weather.
